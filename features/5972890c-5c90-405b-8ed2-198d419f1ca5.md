## 2. Root cause & decisions

ROOT_CAUSE: feature-doc 6641e3ad (changeset-per-run S1, merged) shipped two deliberate NITs marked for S2: (1) SetTaskRun's run_state UPDATE was a bare `COALESCE` with no CAS guard ("parity with SetTaskPR; safe under niwa single-leader" — but the ticket asks S2 to close the TOCTOU regardless, since a future concurrent writer isn't ruled out); (2) a run-container parent deliberately stays task-status='pending' while its run_state advances through open/gating/merging/etc (it is never claimable — guardNotRunContainer refuses ClaimTask/StartTask on it), but the ACK stale-scanner (GetUnackedTasks + checkUnackedTasks in internal/relay/cleanup.go) has no concept of run containers, so it would nag/escalate a container every tick as if it were a plain unclaimed task nobody picked up.

DECISION: (1) CAS-guard SetTaskRun's UPDATE on the run_state value the same call read (`WHERE run_state IS <from>`), matching the codebase's existing CAS idiom (task-status transitions in tasks.go, task-lease reclaim in task_lease.go) — RowsAffected=0 now returns typed CodeRunStateConflict instead of silently landing a stale write. (2) GetUnackedTasks excludes run containers at query time (`run_state IS NULL OR run_state = ''`); MarkTaskAckNotified/MarkTaskAckEscalated are now themselves CAS-guarded (status still 'pending', run_state still empty, not already marked) so the scanner's read-then-act window (a real gap — GetUnackedTasks reads a whole batch, then acts on each task one at a time with a separate write) can't fire a notification for a task that became a container (or was claimed, or was already marked by a concurrent tick) in between. Verified: TestGetUnackedTasksExcludesRunContainers (query-time), TestAckMarkNoOpsWhenTaskBecomesRunContainerMidScan (the literal AC2 scenario — read, then race, then no-op act), TestAckMarkIdempotentAcrossConcurrentTicks (double-fire guard as a bonus of the same mechanism).

Concurrency-test design note (worth recording — cost real debugging time): a goroutine-based test asserting "10 concurrent SetTaskRun(..., open) calls -> exactly 1 winner" is WRONG for this schema, because a same-value run_state restamp is an intentionally idempotent no-op (mirrors SetTaskPR) — every racer that reads the post-winner state will see its own target already achieved and legitimately succeed too; there is no way to get N-1 hard failures out of N racers targeting the identical value. Proving the CAS instead requires either (a) a deterministic white-box test that captures a real "from" snapshot, lets an independent call advance the row, then re-attempts the same guarded UPDATE clause with the stale snapshot (TestSetTaskRunCASRefusesStaleWrite), or (b) N goroutines racing the exact guarded UPDATE clause off ONE shared pre-read snapshot so only the WRITE races, not the READ (TestSetTaskRunCASGuardSerializesConcurrentWriters) — mirrors TestReclaimConcurrentOneWins' pattern (task_lease_test.go), which works reliably because ReclaimTask's precondition (a specific dead holder) is irrevocably consumed by any winner, unlike a same-value run_state stamp.
