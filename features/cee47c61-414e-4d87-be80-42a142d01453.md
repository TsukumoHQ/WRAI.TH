# Decision — suppress Notify/NotifyBroadcast on idempotency dedup-hit (task cee47c61)

ROOT_CAUSE: InsertMessageWithDeliveries correctly short-circuits a retried
send_message (matching idempotency_key) to the existing message — no new
message/delivery row is written. But HandleSendMessage
(internal/relay/handlers_messaging.go) called registry.Notify /
registry.NotifyBroadcast / notifyConversation unconditionally after that
call, regardless of whether it was a fresh insert or a dedup hit. Those are
live SSE/wake pushes, not idempotent like AddToTeamInbox's `INSERT OR
IGNORE` — so a client retry (e.g. after a timeout) still produced a second
wake event for the recipient even though nothing new was delivered. This
partially undermined the duplicate-wake fix task ac328091 set out to land.

Decision: InsertMessageWithDeliveries now returns an additional `dedupHit
bool` (true only when the idempotency key matched an existing message and no
new row was written). HandleSendMessage's three notify branches (team
fan-out, direct/broadcast/conversation) are gated on `!dedupHit`.
AddToTeamInbox stays unconditional since it is already idempotent and
harmless on a dedup hit.

Alternatives considered:
- Detect a dedup hit by comparing timestamps/IDs after the fact in the
  handler. Rejected: fragile (clock skew, no atomicity with the insert
  itself) versus the DB layer, which already knows definitively inside the
  same transaction whether it took the dedup branch.
- Add a second DB method (`InsertMessageWithDeliveriesDedup`) only for the
  two call sites that need the bool, leaving the original 2-return function
  for the other 8 callers. Rejected: duplicates the transaction logic in two
  places, inviting future drift; a single 3-return function with a
  mechanical `_` at unaffected call sites is simpler to keep correct.

Regression test: internal/relay/handlers_messaging_idempotency_test.go
TestSendMessage_DedupHitSuppressesNotify — binds a fake session to the
recipient so SessionRegistry.Notify's send attempt is observable (it logs on
failure to reach a non-existent MCP client), and asserts that log line
appears on the first (fresh) send but not on the dedup-hit retry. Verified
by hand that reverting the `!dedupHit` guard makes this test fail.

Scope: internal/db/messages.go (signature change) + internal/relay/*.go
(handlers_messaging.go behavior change; api.go, api_messages.go,
federation.go, handlers.go, handlers_tasks.go, notifications.go mechanical
call-site updates only, no behavior change) + matching test files.

## Round 2 (reviewer-found gap)

REVIEWER FINDING (round 1 rejection): registry.Notify/NotifyBroadcast was
correctly gated, but handlers_messaging.go's `h.events.Emit(MCPEvent{Type:
"message", ...})` (activity-feed / SSE bus event, no message_id) is ALSO a
wake channel — agentd's wake daemon (sse.rs) gates directly off this
envelope's Type/Priority/MsgType per wake_gating_test.go, with no message_id
to dedup on. It fired unconditionally, so a dedup-hit retry still woke the
recipient through this second channel even with Notify suppressed.

Fix: wrapped the Emit call (and its `action` computation) in the same `if
!dedupHit` guard, direct/broadcast/conversation branch only — the team
fan-out branch never emitted this event to begin with (pre-existing, out of
scope). Added TestSendMessage_DedupHitSuppressesMessageEvent
(internal/relay/wake_gating_test.go) using the existing events.Subscribe()
harness (same pattern as TestSendMessage_EmitsMsgType) to assert no
Type:"message" event fires on a dedup-hit retry; verified by hand that
reverting the guard makes it fail.
