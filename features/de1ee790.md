## 2. Root cause & decisions

# R0 — split token_usage into a separate analytics DB

ROOT_CAUSE: token_usage (~1.6M rows, ~79% of the 402MB coordination sqlite file)
sits inside the coordination hot-path DB. Every hourly Backup() (VACUUM INTO) and
every 5-min Optimize()/checkpoint therefore churns 1.6M telemetry rows that have
nothing to do with coordination — making backups/checkpoints ~5x more expensive
than the coordination data warrants, and bloating every snapshot.

## Decision
Move token_usage (table + its 3 indexes) out of the coordination DB into a sibling
analytics sqlite file (`relay.analytics.db`), ATTACHed as schema `analytics` on
every connection through a per-path ConnectHook driver (`registerAttachDriver`).
Because a Go `database/sql` pool opens connections lazily, the ATTACH must run
per-connection — the ConnectHook is the only reliable place.

- All token_usage queries are single-table (verified: no cross-table JOINs), so
  unqualified `token_usage` resolves to the attached file with **zero query edits**.
- `VACUUM INTO` copies only the main schema, so Backup() snapshots automatically
  **exclude** the attached analytics DB — the backup/checkpoint stops churning
  telemetry and the coordination DB drops ~402MB → ~85MB.
- Migration is **non-destructive + idempotent**: a legacy in-coord token_usage is
  copied into analytics, dropped, and the coord DB VACUUMed once to reclaim pages;
  the branch is skipped once the legacy table is gone (sqlite_master check).
- Raw retention shortened 30d → 14d; a new daily rollup (`token_usage_daily`) is
  refreshed before each purge so older aggregates survive the shorter window.
- Single-writer discipline intact: writer stays `SetMaxOpenConns(1)`; analytics
  attaches read-write on the writer, read-only on the RO reader pool (opened after
  migrate so the file exists). `NewReadOnly` guard-attaches only when the file
  exists (a read-only attach of a missing file fails).

## Rejected alternatives
- **Separate `*sql.DB` handle (no ATTACH).** Cleaner in Go's pooled model, but the
  ticket AC explicitly requires ATTACH, and ATTACH keeps a single logical namespace
  so the existing single-table queries work unchanged and `VACUUM INTO` exclusion
  comes for free. Rejected in favour of the AC-specified ATTACH.
- **ATTACH inside `migrate()` on the single conn (no ConnectHook).** Would attach
  only the writer conn; the RO reader pool's separate connections would not have
  the attach and every dashboard read would fail. Rejected — must be per-connection.
- **Leave retention at 30d.** The raw table is the largest in the DB; without a
  shorter window + rollup the GROUP-BY-over-raw dashboard reads stay expensive.

## Deploy notes (for CTO — relay redeploy is HELD/batched)
- First post-deploy boot on the live ~402MB prod DB runs a one-time `VACUUM main`
  to reclaim pages after the move: a few seconds + transient ~2x disk. One-time,
  before the port binds.
- Forward-only for telemetry: downgrading the binary after this migration makes the
  old code recreate an empty in-coord token_usage and lose visibility of the moved
  rows (telemetry only — no coordination/SSOT data is at risk).
