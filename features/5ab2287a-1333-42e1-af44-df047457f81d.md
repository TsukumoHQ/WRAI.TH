# Decision — P1 resolveTaskID resolves Linear keys (task 5ab2287a)

ROOT_CAUSE: the relay runs in Linear mode where tasks are dual-keyed (id UUID +
linear_key SYN-xxxx + linear_issue_id). db.ResolveTaskID (tasks.go, called by
every get_task/task handler via handlers.go resolveTaskID) matched a full UUID or
a UUID PREFIX only: a Linear key like SYN-3296 fell through to `return prefix`,
so get_task on a Linear key resolved to nothing even though the row exists with a
title. Downstream, agentd's get_task missed → QaRec empty → the scribe emitted
"⚠ untyped record" / "task SYN-xxxx" banners (~300 on synergix-prod).

DECISION (relay lane — the identity/SSOT owner; NOT agentd reaching into relay.db,
which niwa-cto ruled a layering violation + WAL-contention risk,
DEC-niwa-gate-linear-resolution): add a Linear-key fallback to ResolveTaskID,
tried ONLY when the existing id resolution misses.

- The <36-char UUID-PREFIX path is byte-for-byte UNCHANGED and tried first (fast
  path, no regression for UUID lookups): exact-1 → return, >1 → ambiguous error,
  0 → fall through.
- The >=36-char full-UUID branch now VERIFIES the id exists (one indexed PK
  lookup) and returns it; a real UUID still resolves to itself (no regression).
  Only on a MISS does it fall through — necessary because a linear_issue_id is
  itself a 36-char UUID, so it lands in this branch, not the prefix path.
- Fallback: resolveLinearTaskID does a single project-scoped indexed query
  `SELECT id FROM tasks WHERE (linear_key = ? OR linear_issue_id = ?) AND
  project = ? ORDER BY dispatched_at ASC, id ASC LIMIT 1`. Read-only, never
  cross-project. Deterministic on the rare multi-match (oldest-dispatched wins,
  tie-broken by id) so the same input always resolves to the same task.
- New index idx_tasks_linear_key on tasks(linear_key) (idx_tasks_linear_issue
  already covers linear_issue_id) so the fallback is a lookup, not a scan.
  Additive CREATE INDEX IF NOT EXISTS — backward-safe.

AMBIGUITY: the prefix path keeps its existing hard error (a UUID prefix hitting
multiple ids is a caller error). The Linear fallback instead resolves
deterministically (LIMIT 1 by dispatched_at) rather than erroring — within a
project a linear_key is effectively unique (the fan-out mirrors one row per
project), and get_task must return the real task, not fail; the deterministic
pick makes a pathological duplicate stable rather than flaky.

REJECTED — agentd queries relay.db directly: layering violation + a second
reader on the single-writer WAL (niwa-cto ruling). The resolution belongs in the
relay, where it fixes every consumer (MCP + agentd gate) at once.

REJECTED — make linear_key the primary lookup: would regress the hot UUID path;
the fallback-on-miss keeps UUID lookups first + fast.

CROSS-LANE: gate-lead's a1082a6f (QaRec goal/dod copy from get_task) lights up
the moment this lands — flagged, no coordination needed here (this is the
read-only resolver half).
