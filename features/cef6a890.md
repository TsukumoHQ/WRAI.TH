# Decision — cef6a890: message-length percentiles on /api/metrics/comms (S4)

ROOT_CAUSE: The comms S4 endpoint (GET /api/metrics/comms) already shipped
(route api.go:203, handler comms_metrics_api.go, db.CommsMetricsSnapshot, tests)
covering no-wake share, per-sender action_required distribution, read-latency
buckets, and coalescing candidates. But one AC field was absent: the message-length
percentiles (p50/p90/avg). The DEC-relay-comms-discipline-1 analysis concluded
verbosity is SUBSTANCE-length, not preamble — so message length is the metric that
actually tracks hygiene, and it was the missing half of the standing measurement.

## Decision
Add a MsgLength block (avg, p50, p90, sampled) to CommsMetricsSnapshot, aggregating
LENGTH(content) over the SAME project + window scoping as the rest. SQLite has no
PERCENTILE_CONT, so p50/p90 are read off the LENGTH-ordered result by OFFSET
(offset = int(frac*(n-1))); avg + count come from one AVG/COUNT pass. Best-effort
like every other sub-query — a failing read leaves zeros, never 500s the scrape.
Read-only (RO pool), no schema change, additive JSON field.

Unscoped (no ?project=) samples nothing (WHERE project=''), consistent with the
existing snapshot — documented in the handler comment. LENGTH is SQLite's character
count (chars≈bytes for ASCII dev chatter); noted in the field comment.

## Rejected alternatives
- A window function (NTILE/PERCENTILE_CONT) for percentiles: SQLite lacks
  PERCENTILE_CONT; an NTILE/ROW_NUMBER subquery to pick the p50/p90 rows is less
  readable than the two OFFSET reads and no more correct on a bounded window.
- Byte-exact length via CAST(content AS BLOB): rejected as over-engineering — char
  count is the standard "message length" and matches the analysis; documented.
