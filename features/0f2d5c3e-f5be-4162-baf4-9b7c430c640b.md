# Decision: canonicalize project-name case at the DB registry (ticket/e2f5ad14 #3)

ROOT_CAUSE: Project-name canonicalization was applied at the handler read
boundaries (relay.NormalizeProject in resolveProject / projectFromRequest) and
by a boot migration, but two project-registry WRITE paths bypassed it, so a
mixed-case or underscore spelling could still create an unreachable namespace or
a lost lookup:
  1. HandleCreateProject lower-cased the name but did NOT fold `_`→`-`, so
     `create_project("synergix_prod")` stored "synergix_prod" while every
     normalized handler resolves to "synergix-prod" — an orphan namespace, and
     its own ListAgents "already_configured" cross-check missed the agents
     already registered under the canonical name.
  2. HandleDeleteProject / the REST delete + planet-type update passed the raw
     name straight to the DB, so deleting "Foo" never matched the stored "foo".

## Decision
Canonicalize inside the DB project-registry helpers themselves — the single
choke point every caller (MCP handlers + REST) routes through — instead of
chasing each handler. New unexported `canonicalProject(name)` in the db package
(TRIM+LOWER+`_`→`-`, exempting "" and internal "_"-prefixed pseudo-projects) is
applied in EnsureProject, GetProject, UpdateProjectPlanetType, DeleteProject,
ProjectRequiresTypedTicket, SetProjectRequiresTypedTicket. Also fixed
HandleCreateProject to use NormalizeProject (not bare ToLower) so its local
`name` (used for the ListAgents cross-check + the echoed response) matches what
EnsureProject stores, and HandleDeleteProject to normalize its echoed response.

## Why this shape
- **DB-layer choke point** (vs. fixing only the two handlers): bypass-proof —
  any future caller, or a handler that forgets to normalize, still can't create
  a case-split duplicate. Directly satisfies "canonicalize on read+write."
- **Idempotent + migration-safe**: canonicalProject is a no-op on already-canon
  names, and existing mixed-case rows are already collapsed by the existing
  boot pass migrateNormalizeProjects. No schema change, no new migration, no
  writer added — pure string normalization before the existing queries.
- Scoped to the projects-registry helpers only, NOT every project-keyed query
  (inputs are already normalized at the write boundary via resolveProject);
  avoids sprinkling LOWER() across hot generic reads.

## Lockstep note (reviewer)
canonicalProject MUST stay in lockstep with relay.NormalizeProject and the SQL
form in migrateNormalizeProjects — one rule, three expressions. Documented in
the helper's doc comment. Not unified into a shared leaf package to keep this a
minimal, low-risk P2 (db cannot import relay); flagged as a possible follow-up.

## Rejected alternatives
- Fix only the two handlers: leaves the REST paths + any future caller exposed.
- New destructive migration to rewrite rows: unnecessary — the additive boot
  migration already canonicalizes existing data; the gap was the live write path.
- Move NormalizeProject to a shared package both relay+db import: cleaner SSOT
  but a larger rewire across ~6 call sites; deferred, not needed to close #3.
