## 2. Root cause & decisions

# 1b89a212 — R2+R4: index the tasks sweeper SCANs + bound/narrow statsTasks

ROOT_CAUSE: Three tasks-table reads run hot and unbounded. (R2) ListStrandedPRTasks
(PR-reconcile sweeper) and GetUnackedTasks (ack sweeper) each ran a full-table
tasks SCAN every 2/5 min — no index covered their WHERE. (R4) statsTasks pulled
all ~50 task columns for every non-archived row of a project on every dashboard
poll, unbounded — heavy per-poll scan + allocation that grows with the board.

## Decision
R2 — add two additive, idempotent indexes (CREATE INDEX IF NOT EXISTS):
- `idx_tasks_pr ON tasks(pr_state) WHERE pr_number IS NOT NULL AND archived_at IS NULL`
  — a PARTIAL index scoped to the PR-linked, non-archived candidate set, so it
  stays tiny (most tasks have no PR) and ListStrandedPRTasks' WHERE implies its
  partial predicate → SEARCH … USING INDEX idx_tasks_pr.
- `idx_tasks_status_dispatched ON tasks(status, dispatched_at)` — GetUnackedTasks
  SEARCHes status='pending' then range-scans dispatched_at.

R4 — statsTasks now selects only the 18 columns the stats aggregation actually
reads (new `statsTaskColumns` + `scanStatsTask`, verified against every field
access in GetAgentStats and its compute* helpers), newest-first and bounded by
`statsTaskCap` (20000). The cap is a pathological-growth CEILING, not a functional
filter: it sits far above any real project's task count, so results are unchanged
in practice; rows are taken newest-first so a project that ever exceeded it keeps
its most relevant (recent) tasks.

Scope: internal/db/db.go (2 indexes), internal/db/agent_stats.go (narrow + bound),
internal/db/task_index_eqp_test.go (new EQP evidence). No cross-lane/shared file
beyond db.go's migrate (own lane). No hot-path write, single-writer untouched.

## Rejected alternatives
- **Bare `LIMIT` with no ORDER on statsTasks.** Non-deterministic truncation would
  drop arbitrary tasks and corrupt the derived cycle list / burndown in the
  pathological case. Rejected — ORDER BY dispatched_at DESC makes any truncation
  deterministic and least-harmful (keep newest).
- **A supporting index for statsTasks' ORDER BY (project, dispatched_at).** The
  sort is negligible at real scale (bounded top-N; real projects are far under the
  cap) and an extra index costs on every task insert/update. Not worth it; left out.
- **Non-partial idx_tasks_pr on pr_state alone.** Would index every task's
  (mostly NULL) pr_state; the partial predicate keeps the index to the handful of
  PR-linked rows.
