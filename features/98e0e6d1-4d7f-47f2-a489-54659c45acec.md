# Decision — P1 backup retention ROOT fix (task 98e0e6d1)

ROOT_CAUSE: ~/.agent-relay filled to 11G on synx-prod (93% root disk) because
nothing retires full-DB backup copies. Two sources, both = no retention policy:

1. PERIODIC SNAPSHOT WRITER (in-repo): `BackupKeep = 12` (cleanup.go) — the
   hourly `database.Backup(keep)` rotates relay.db.bak.0..11, each a FULL VACUUM
   INTO copy (~635M). 12 × 635M ≈ 7.6G. The rotation logic (db.go Backup) is
   correct; the retention COUNT was the bomb, and it was a compile-time const
   (not tunable per host).

2. ONE-OFF UPDATER/OPS BACKUPS (out-of-repo): relay.db.bak-preupg, PRE-RESET,
   v115-broken and analytics siblings are created by the HOST updater / ops
   (autoupdate.log; NOT the relay Go binary — confirmed: internal/cli/update.go
   only does the atomic binary swap, no DB copy; grep of install.sh / *.go /
   *.sh / *.ps1 for preupg|PRE-RESET|-broken|bak- = zero in-repo hits). Nothing
   ever prunes them.

DECISION (in-lane root fix — the relay owns ~/.agent-relay and a healthy boot IS
the post-upgrade verification the host updater lacks):

1. RETENTION COUNT config-driven + sane default. `BackupKeep=12` const →
   `DefaultBackupKeep=3` + `resolveBackupKeep()` reading `RELAY_BACKUP_KEEP`
   (positive int; invalid/≤0 falls back to default, never 0 = never zero
   recovery points). Default 3 bounds snapshot disk to ~3×snapshot; a host that
   wants a wider window raises the env. Rotation logic unchanged.

2. DATA-DIR GC (new db.PruneStaleBackups, wired into StartCleanup at boot AND
   after each successful snapshot). Removes: superseded numbered snapshots
   (bak.N, N≥keep — catches slots orphaned when keep is lowered) + aged one-off
   updater/ops backups (name matches the relay.db / relay.analytics.db prefix
   AND a backup marker: .bak/.bak.N/bak-/broken/PRE-RESET/preupg/.backup/.old).
   SAFETY (ticket constraints): the live coord + analytics DBs and their
   -wal/-shm are NEVER touched; the single NEWEST one-off is always kept as the
   last known-good rollback point; one-offs are pruned only once older than
   `ForeignBackupMinAge` (24h) so a just-upgraded host keeps its pre-upgrade
   copy for a recovery window. Only unlinks superseded copies → idempotent +
   live-host-safe. Runs at boot = the "healthy post-upgrade check" that lets the
   relay prune the updater's stale backups the updater never cleans.

3. ANALYTICS DB (RC3) — ASSESSED, VACUUM DEFERRED with rationale. The live
   relay.analytics.db row growth is ALREADY bounded (shipped): PurgeOldTokenUsage
   trims raw token_usage to 14d + the daily rollup keeps aggregates; SQLite
   reuses freed pages for new inserts, so the file PLATEAUS rather than growing
   unbounded. The incident's runaway bloat was the full-COPY backups (covered by
   the GC above — analytics.db.bak-* is pruned). A live `VACUUM analytics` to
   shrink the file on disk is exactly what R0 (the analytics split) deliberately
   kept OFF the coordination hot path (VACUUM INTO/checkpoint of ~1.6M rows =
   the serve-wedge class); adding a heavy live VACUUM on a P1 is a worse risk
   than the bounded file it would reclaim. Deferred — reopen only if the live
   file (not its backups) is shown to grow past the 14d-retention plateau.

REJECTED — one-time cleanup script: the ticket is explicitly a ROOT fix. A
script doesn't stop re-accumulation on every host via auto-update; config
retention + the standing GC do.

REJECTED — relay deletes ALL relay.db.* siblings: too broad (could nuke a file
an operator parked). The GC requires a backup-marker token AND keeps the newest
one-off AND age-gates, so an unrelated relay.db.notes survives (tested).

REJECTED — fix the updater's backups in the updater: the updater is out-of-repo
(host/ops). The in-lane, ships-everywhere fix is the relay pruning its own data
dir on healthy boot; flagged for the host-updater owner as a complementary
teardown if they want it belt-and-suspenders.
