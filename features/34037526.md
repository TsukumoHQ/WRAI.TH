## 2. Root cause & decisions

ROOT_CAUSE: Two independent bugs stacked to produce the 2026-08-22 serve wedge + the ~9min silent-startup symptom.

(1) Serve wedge: `Backup()`'s `VACUUM INTO` ran on `d.conn`, the app's single-connection writer pool (`SetMaxOpenConns(1)`) shared by every write. A slow VACUUM on a large DB checked that connection out of the pool for the whole copy; every other write then blocked on Go's `database/sql` pool wait, which has no timeout on any call site — the observed "alive, TCP open, HTTP silent, one thread usleep-spinning in sqlite's busy handler, everything else parked" signature.

(2) Startup silence: `startServer()` in main.go ran DB init/migrations (`db.New()`) before opening the TCP listener or logging anything. On a large DB this could block minutes with 0% CPU, no port bound, no log line — indistinguishable from a hang from the outside, and it's what made wedge #2's real cause (1) hard to tell apart from a plain slow start.

DECISION: (1) fixed by giving `Backup()` its own dedicated read-only connection for `VACUUM INTO`, never touching `d.conn`; also added `writerExec`/`beginWriterTx` helpers so every writer-pool call is now bounded by a context timeout (15s, var not const) — go-sqlite3 honors ctx cancellation via `sqlite3_interrupt`, confirmed against the vendored source, so a stuck call now aborts server-side instead of hanging forever. Mechanically swapped every `d.conn.Exec`/`d.conn.Begin*` call across `internal/db/*.go` (25 files) to the bounded helpers — no query/column logic touched.

(2) fixed by opening the TCP listener (`net.Listen`) and logging "listening on <addr>" in main.go BEFORE `db.New()`/migrations run, then handing the already-open listener to a new `Relay.Serve(ln)` once init finishes. `ListenAndServe(addr)` (which binds internally) is kept for callers that don't need to bind early; both share a new `buildHandler()` extracted out of the old `ListenAndServe`.

REJECTED ALTERNATIVE: content-based dedup in `InsertMessageWithDeliveries` for the outbox-replay bug (part B of the ticket) — byte-identical project/from/to/type/subject/content within a 30s window short-circuiting to the existing message. Broke 5 existing tests (heartbeats, repeated status, test fixtures legitimately send identical-content messages from the same sender back to back). Reverted cleanly. A correct fix needs a caller-supplied idempotency key (an API signature change) — real work, left as a follow-up, not done here.

[LEGACY_OPPORTUNITY]: `relay.analytics.db.parked-2026-08-22` (320MB) sitting on disk is the inert, already-applied backup from the one-time `migrateTokenUsageToAnalytics` backfill (guarded/idempotent, already ran — the live `relay.analytics.db` holds the migrated data). No restore/migrate action needed; safe to `rm` as housekeeping whenever convenient, not blocking this fix.
