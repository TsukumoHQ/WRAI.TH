# Decision — P0 token_usage→analytics migration idempotent + partial-safe (task 5d06f3e6)

ROOT_CAUSE (internal/db/db.go, migrateTokenUsageToAnalytics): the one-time legacy
backfill runs three SEPARATE statements — copy, DROP, VACUUM — and VACUUM cannot
run inside a transaction, so the block is not atomic. The copy was a plain
`INSERT INTO analytics.token_usage (id,...) SELECT ... FROM main.token_usage`
(old db.go:1389). If a prior migration copied rows into the analytics DB then
crashed before `DROP TABLE main.token_usage`, the next boot finds the legacy
table still present AND analytics already holding those ids; the plain INSERT
re-copies them and violates the analytics PK: `UNIQUE constraint failed:
token_usage.id`. That error propagated up as fatal (db.go:940 `migrate
token_usage to analytics: %w`), aborting init → systemd restart → re-crash =
crash-loop. synx-prod (prod) hit this on the v1.15 auto-upgrade: ~34 restarts
10:27–10:32 UTC, recovered ONLY by a data-losing DB reset (relay.db 640M→82M).
The docstring even claimed "idempotent" — it was not, for the partial case.

DECISION: make the backfill conflict-tolerant and non-fatal.
1. Copy is now `INSERT OR IGNORE` — any id already in analytics (partial prior
   run or duplicate) is skipped, so the copy can never violate the PK and never
   aborts init.
2. Drop is gated on a FULL-COLUMN match: DROP main.token_usage only when every
   legacy row is present in analytics with identical content. If OR IGNORE
   skipped a legacy id because analytics holds a DIFFERENT row under that id
   (id-space overlap, content mismatch — e.g. a legacy DB restored over a
   live-grown analytics), the legacy table is KEPT and logged, never dropped.
   Zero data loss.
3. Every step in the backfill block (copy / count / drop / vacuum) degrades to a
   logged non-fatal skip on error and returns nil — init NEVER aborts for this
   migration again. A retained legacy table reconciles on a later boot.

REJECTED — dedupe the source (SELECT DISTINCT/GROUP BY id): main.token_usage.id
is AUTOINCREMENT PK so the source has no intra-table duplicates; the conflict is
cross-DB (analytics already has the id), which INSERT OR IGNORE handles directly.

REJECTED — id-only drop guard (WHERE NOT EXISTS ... a.id = m.id): it would drop
the legacy table when analytics has a DIFFERENT row under a colliding id,
silently losing the legacy row (a data-safety REGRESSION vs the old code, which
crashed but preserved main). Full-column match is airtight.

REJECTED — wrap copy+drop in a transaction: VACUUM cannot run in a transaction,
and a marker-guarded transaction adds surface for no gain once the copy is
idempotent; OR IGNORE + content-gated drop is retry-safe by construction.

INVESTIGATION (AC #5, reset path): the reset was a manual/updater recovery FORCED
by the crash-loop, not an automatic code path in this repo. With the migration
now conflict-tolerant + non-fatal, init can never crash-loop on token_usage data,
so the reset that caused the data loss is never triggered for this migration
again. No reset code to remove; the fix removes its cause.
