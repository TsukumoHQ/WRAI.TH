# Decision: delete-path orphan cleanup — DeleteAgent / DeleteTask (task d21e7ef6)

ROOT_CAUSE: Follow-up to 52f7502d (which fixed only the crashing default-purge FK
waterfall). Two other delete paths leave LOGICAL orphans that don't trip the one
enforced FK (deliveries.message_id), so they fail silently rather than crash:
- DeleteTask (tasks.go) hard-deleted ONLY the tasks row, leaving task_progress_notes
  (task_id NOT NULL, reachable only via the task) as dead rows keyed to a vanished
  task id — never queryable, never cleanable.
- DeleteAgent (agents.go) is a soft UPDATE status='deleted'; the question was whether
  its agent-scoped rows (messages/deliveries/memories/team_members/tasks) are orphans.

## Decision (per path)
1. **DeleteTask — clean the owned child.** Wrap in one tx (DeleteProject-cascade
   precedent): child-first DELETE FROM task_progress_notes WHERE task_id, then the
   task row. task_progress_notes is the ONLY table whose rows are owned by (reachable
   only through) a task.
   - LEFT inert on purpose: `messages.task_id` is a soft cross-reference — a message
     about a task is an independent entity with its own deliveries (the enforced FK) +
     reads and legitimately outlives the task; cascading would over-delete.
     `tasks.parent_task_id` (subtasks) is a soft link — deleting a parent must not
     silently nuke its children. Test asserts a subtask survives.
2. **DeleteAgent — documented intentional soft-delete (tombstone).** The agent row is
   flipped to status='deleted' and KEPT, so every dependent references a present-but-
   tombstoned row — no logical orphan, no child cleanup needed. T5-consistent (degrade,
   don't destroy) and reversible (re-register the same name flips back to 'active',
   history intact). A hard purge of an agent's rows only happens via the ordered
   DeleteProject cascade. Documented in a doc comment.
3. **DeleteConversation** — no standalone path exists (only via DeleteProject cascade);
   nothing to fix.

No schema migration (52f7502d precedent). memories stay tombstoned via DeleteAgent's
soft-delete; DeleteTask doesn't touch memories.

## Rejected alternatives
- **Cascade DeleteTask into messages.task_id:** over-deletes independent message
  entities (+ their enforced-FK deliveries). Wrong ownership model.
- **Cascade into subtasks:** silently destroys children on a parent delete — surprising
  and lossy. Left as a soft dangling link instead.
- **Hard-delete agent rows + cascade dependents:** abandons the T5 tombstone model and
  breaks re-register revival + history. Kept the deliberate soft-delete.
