## 2. Root cause & decisions

# Decision — 121f0ff5: native backlog status (groomed, not claimable until promoted)

ROOT_CAUSE: Every dispatch lands as `pending`, which is immediately claimable. There was no
way to GROOM a ticket (write it up, park it) without an idle agent picking it up out of order.
Moving it to a "backlog" BOARD doesn't help — a board is just a grouping; the task stays
pending/claimable. The founder wants a real backlog COLUMN: groomed work that is visible but
does not get worked until a human/lead activates it.

## Decision
Add a native `backlog` task status that gates CLAIM, enforced through the existing lifecycle:
- `validTransitions`: `backlog → {pending, cancelled}`, and `pending → backlog` (de-groom).
  Since backlog never reaches `accepted`, a claim (→accepted) fails validation → a backlog task
  is non-claimable. transitionTask surfaces it as a typed `TASK_STATE_CONFLICT` ("promote it
  first"), not a silent accept. One choke, no per-path guard.
- `db.DispatchTask(..., backlog bool)`: create straight into backlog so grooming needs no
  follow-up move. `dispatch_task` exposes a `backlog` flag. A backlog dispatch SKIPS every claim
  signal in dispatchCore — no P0/P1 push, no per-agent inbox delivery, no `task.dispatched`
  event (only a visual `task/backlog` event for the board) — so no agent wakes for or claims it.
- `db.PromoteTask` (backlog→pending, idempotent on already-pending) + a `promote_task` tool.
  Promotion announces the task exactly like a fresh dispatch via a new shared `announceClaimable`
  helper (extracted from dispatchCore), so a promoted task surfaces the instant it's claimable.
- Orthogonal to boards: `move_task` changes board_id only; the claimable gate is the status.
  Existing pending/in-progress/in-review are untouched.

The tool-schema budget was raised 55296 → 56320 (55 KiB) in the same PR for the genuinely new
`promote_task` surface — the sanctioned path per the toolsize_test contract (descriptions were
trimmed to the bone first).

## Rejected alternatives
- A `claimable bool` column instead of a status value: rejected — a status keeps the ONE
  lifecycle/validTransitions the whole system already reasons about (audit, board, reconcile),
  and the claim-gate falls out of the transition graph for free.
- Making promote a raw transitionTask call: rejected — transitionTask has no same-status edge, so
  promote on an already-pending task would be an invalid pending→pending transition (nil task);
  PromoteTask short-circuits that as an idempotent no-op.
- Gating claim with an extra guard clause in ClaimTask: unnecessary — validTransitions already
  refuses backlog→accepted; the typed message is added in transitionTask, no extra read.

## Scope
db (validTransitions, transitionTask guard + backlog UPDATE case, DispatchTask flag, PromoteTask),
relay (dispatchCore backlog skip + announceClaimable + HandlePromoteTask + dispatch_task flag +
promote_task tool/registration), and the DispatchTask/dispatchCore signature ripple to
cron/webhook_signal/api/batch (all pass backlog=false) + every DispatchTask test caller. No
schema/migration — `backlog` is a new value in an existing TEXT status column.
