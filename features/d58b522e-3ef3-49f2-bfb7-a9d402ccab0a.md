## 2. Root cause & decisions

# niwa steal #9 — webhook-triggered dispatch (signal → typed ticket)

ROOT_CAUSE: External signals (CI failure, Sentry error, any event) had no path into fleet
work — a human had to notice and hand-dispatch a task. The relay already had signed inbound
webhook infra (TSU-52: HMAC-verified /api/webhooks/github → durable events outbox) but it only
fed the notify-rules engine, never created a ticket. Missing: a signal → typed ticket → normal
dispatch loop.

## Decision
Add `POST /api/webhooks/signal` — a generic signed inbound signal that becomes a typed ticket
routed through the SAME dispatch pipeline as a hand-dispatched task.

- **Signature-first**: HMAC-SHA256 over the body (`X-Signal-Signature-256: sha256=<hex>`,
  secret `RELAY_SIGNAL_WEBHOOK_SECRET`), verified BEFORE parsing (reuses the shared HMAC
  verifier). Unset secret → 503 (refuse, never an unauthenticated task-injection sink).
- **Config-gated per source**: `X-Signal-Source` keys an operator setting `signal_source:<src>`
  = `{"profile","priority?","board_id?"}`. No config → 403. Endpoint is INERT until an operator
  enables a source. The routing **lane comes from operator config, never the untrusted payload**
  — an external signal cannot target an arbitrary profile.
- **Idempotent**: `X-Signal-Delivery` is the key; the events outbox INSERT-OR-IGNOREs on it, so
  an at-least-once redelivery is a no-op (no dup ticket) and every accepted signal is journaled.
- **Reuses the dispatch pipeline**: refactored the create+notify+emit tail of HandleDispatchTask
  into a shared `dispatchCore`, so a signal-created ticket is indistinguishable from a
  hand-dispatched one (lane notified, task.dispatched emitted). No pipeline drift.
- **Inbound-only**: the relay never reaches out; a host-side forwarder delivers signals to the
  loopback endpoint (same model as the GitHub webhook, same auth middleware).

## Rejected alternatives / trade-offs
- **A new notify-rule action `dispatch`** (vs a dedicated endpoint): rejected — the notify-rules
  engine is the engine lane; a focused endpoint keeps this in the webhook/ingest + task-create
  lane and makes signature/config-gate/idempotency explicit.
- **Ordering (dedup-first vs create-first)**: dedup-first (consume delivery id, then create). If
  create fails on a rare writer error the ticket is lost rather than duplicated — chosen because
  the requirement is "no dup tickets per signal"; a lost ticket on a DB-writer error (which would
  fail everything anyway) is the lesser evil.
- **Free-form ticket**: a signal can't supply goal/AC/dod, so typed-ticket enforcement (an
  interactive-dispatch policy) does not apply on this path.
