# comms-discipline S1 — action_required tag + guard-first wake predicate

Branch: wraith/comms-discipline-s1 → main · Task a51a784b · Design f669f3a5 · SSOT DEC-relay-comms-discipline-1 · CTO greenlit S1/S3/S4 (S2 held)

ROOT_CAUSE: 30.7% of wake-capable relay messages carry NO action (status-as-notification, MERGED-announce, poll-reply responses) yet wake a busy agent, because the wake signal (`UnreadCountForAgent` = count of `queued` deliveries) is TYPE-AGNOSTIC and the only "no-wake" path (ack/fyi) is a fragile niwa-daemon type-heuristic living OUTSIDE the relay control plane. This slice makes the wake decision a first-class, sender-declared, guard-protected relay property.

## Decision (code-is-law: enforce SHAPE, never judge content)
- **Additive column** `messages.action_required TEXT` (ensureColumns, nullable) — `{ask|do|decide|none}`.
- **send_message** gains an OPTIONAL `action_required` param (validated). Omitted ⇒ the relay DERIVES it server-side from `(type, reply_to)`:
  - task→do, question/user_question→ask
  - response→none if reply_to nil, else INHERIT the parent message's tag (an answer to a question wakes the asker)
  - notification/status/fyi/ack/message→none (named report types)
  - unknown/unlisted type→**do (wake)** — never silently suppress a type we don't recognize
- **Guard-first wake predicate** in `UnreadCountForAgent`: a delivery counts toward wake iff
  `P0 OR type IN (question,user_question,task) OR COALESCE(action_required,'do') != 'none'`.
  The guards sit BEFORE the tag, so `none` can NEVER suppress a P0/question/task wake even if mis-tagged. `COALESCE(...,'do')` ⇒ a legacy/older-client NULL row still WAKES (no fleet break).
- `none` messages **stay fully visible in get_inbox** (non-destructive peek preserved) — they are only excluded from the wake COUNT.

## Why no fragile "blocked type" guard
Task blocks notify via `registry.Notify` = ephemeral SSE, NOT stored messages, so they are outside the wake-COUNT path entirely. And Ruling-3 (CTO-CONFIRMED): a blocker-escalation is a DELIBERATE explicit send (a `question`, or an explicitly-tagged message), not a passive list entry — already covered by the guard's question/tag clauses. No stored "blocked" type to special-case.

## Scope / lockstep safety
- The messages table has 8 inline SELECT+scan sites with no shared column const. To AVOID lockstep drift, action_required is touched ONLY at INSERT (store) and in the wake COUNT (WHERE-only, no scan). The model field is populated on the insert return + anywhere a query explicitly selects it; the 8 existing scans are UNTOUCHED → zero drift risk.
- Single-writer intact: inserts on the writer conn; the response-inherit parent lookup uses the RO pool and never fails the insert. No new hot-path write.
- 8 production callers of `InsertMessageWithDeliveries` + all test callers updated to the new `actionRequired string` param ("" = derive). Mechanical.

## Backward-compat
Additive nullable column; NULL ⇒ wakes (COALESCE 'do'). Old binary + new DB and new binary + old DB both boot. Existing clients that never send the param get correct derived behavior. No destructive change.
