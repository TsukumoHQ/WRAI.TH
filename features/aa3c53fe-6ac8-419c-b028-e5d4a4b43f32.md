# Decision: deadletter self-GC (bounded growth) — aa3c53fe

ROOT_CAUSE: The T6 deadletter journal (durable capture of expired-UNREAD
deliveries) was deliberately exempted from the message-retention GC so a
TTL-expired P0/P1 never vanishes — but that left it with NO reclamation path at
all. Every expired-unread delivery is journaled forever; under long-running
fleet operation the table grows unbounded.

## Decision
Give the deadletter table its own long-horizon retention sweep, priority-aware:
- `PurgeOldDeadletter(shortMaxAge, longMaxAge)` in internal/db/deliveries.go.
  Non-P0/P1 rows reclaimed once older than `shortMaxAge` (30d); P0/P1 — the
  critical traces a human may still need to audit — kept far longer and only
  reclaimed past `longMaxAge` (180d). Keyed on `expired_at` (capture time).
- Wired into the existing 5-min cleanup goroutine (StartCleanup) right after the
  audit-log purge, gated + logged like the other purges. Constants
  DeadletterShortRetention / DeadletterLongRetention in relay/cleanup.go.

## Why this shape
- **Batched, writer-friendly**: deletes a bounded id-set per statement
  (`DELETE … WHERE id IN (SELECT id … LIMIT 500)`) in a loop, so a large backlog
  is trimmed across several small writes instead of one long-locking DELETE. The
  `id IN (SELECT … LIMIT ?)` form works without the sqlite UPDATE/DELETE-LIMIT
  compile flag. Cutoffs are computed once before the loop, so the eligible set
  is fixed and the loop always terminates.
- **Idempotent**: once nothing is old enough the sweep deletes 0 (tested).
- **Never touches live deliveries/messages**: operates solely on the deadletter
  table; the T6 "P0 must not vanish silently" guarantee is preserved — P0/P1 are
  simply kept far longer, not dropped early.
- Unknown/other priorities fall into the short-horizon bucket (only P0/P1 get
  the long horizon) — safest for the "bounded" goal.
- No schema change. Updated the deadletter schema comment in db.go (it claimed
  the table is "NOT touched by the GC" — now true only of the *message*-retention
  GC; it has its own sweep).

## Rejected alternatives
- Keep P0/P1 forever: technically satisfies "or keep far longer" but reopens the
  unbounded-growth concern the ticket is closing; a 180d horizon stays bounded.
- Single unbatched DELETE (like PurgeExpiredMessages): simpler but can hold the
  single writer on a large backlog; batching is cheap insurance on a table that,
  by definition, only grows.
- sqlite `DELETE … LIMIT`: needs a compile flag not guaranteed in this build.
