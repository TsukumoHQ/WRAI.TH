# Decision — 1dc3be08: get_inbox default path off the whole-project scan (relay-perf R1)

ROOT_CAUSE (empirical, via EXPLAIN QUERY PLAN on a seeded DB):
1. `HasDeliveries()` (deliveries.go) ran `SELECT COUNT(*) FROM deliveries` on EVERY default
   get_inbox call — a whole-TABLE count (every delivery row, all projects) just to pick the
   inbox query. Plan: `SCAN deliveries USING COVERING INDEX` visiting all rows.
2. `getInboxLegacy` (messages.go, the fallback when deliveries is empty) used one
   OR-of-everything predicate (`to_agent=? OR broadcast OR conversation IN (...)`) that
   defeated every index. Plan: `SEARCH m USING idx_messages_project (project=?)` = scan ALL
   project messages per call, + `USE TEMP B-TREE FOR ORDER BY`.

Note on the default PROD path: it already routes through the indexed deliveries table
(`GetInboxViaDeliveries`: SEARCH idx_deliveries_agent_state + a bounded per-agent filesort),
and the most-polled wake signal (`UnreadCountForAgent`) is already a COVERING-index lookup.
So the biggest real per-poll win is #1; #2 is the AC's named legacy target.

## Decision
1. `HasDeliveries`: `SELECT 1 FROM deliveries LIMIT 1` — stops at the first row (O(1)) instead
   of counting the whole table. Identical boolean semantics (true iff ≥1 delivery); monotonic
   in practice so the first-row hit is the norm.
2. Add `idx_messages_project_to(project, to_agent, created_at)` (additive, CREATE INDEX IF NOT
   EXISTS) and rewrite `getInboxLegacy` as a UNION ALL of three mutually-exclusive,
   index-driven branches — direct DM / broadcast / conversation. Each branch SEARCHes the new
   index by (project, to_agent), so row selection is O(agent-inbox), not O(project). UNION ALL
   (not UNION) because the branches are disjoint (to_agent is one value; conversation_id NULL
   vs NOT NULL) — no dedup sort. Common filters (expiry/ttl/unread/priority/from/since) + the
   priority,created_at ordering wrap the union, preserving the original semantics exactly.

EXPLAIN after: each legacy branch → `SEARCH m USING INDEX idx_messages_project_to`; the
whole-project SCAN is gone.

## Rejected alternatives
- Adding the index WITHOUT splitting the OR: rejected — verified the full OR query still plans
  `SEARCH idx_messages_project (project)` (project-broad); SQLite won't OR-optimize across the
  broadcast + conversation-subquery terms. The UNION split is required for SEARCH-by-agent.
- Killing the TEMP B-TREE in GetInboxViaDeliveries (default path): the ORDER BY is on joined
  message columns over the agent's bounded delivery set (LIMIT 50) — a small, acceptable
  filesort; removing it needs denormalising priority/created_at onto deliveries (bigger change,
  out of scope for R1). Left as-is; noted for a future ticket.
- Caching HasDeliveries as a monotonic bool: the O(1) LIMIT-1 query is already free and avoids
  any cache-staleness reasoning; not worth the state.

## Scope
db.go (one additive index), deliveries.go (HasDeliveries), messages.go (getInboxLegacy),
+ tests. getInboxLegacy is the legacy/fresh-DB path (prod uses deliveries) — the rewrite meets
the AC's "SEARCH not SCAN" + protects fresh/empty-deliveries DBs; #1 is the prod per-poll win.
